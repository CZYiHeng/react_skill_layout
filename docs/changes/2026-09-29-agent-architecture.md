## 0. 本文档的读法

那篇清单给了九项关注点，并按投入产出排了落地优先级。本文档做两件事：

1. **第 1 部分——整体框架**：把九项关注点在**本项目的现状**上逐条定位，给出**框架层**的设计（哪些已有、哪些缺、缺的怎么补）。这一部分是"地基"，所有能力包共用。
2. **第 2 部分——编码能力**：用框架提供的机制，把「编码能力包」设计完整。这是**本次要做的**。
3. **第 3 部分——后续能力**：需求理解 / QA 审查的**接口预留**（只定边界，不设计细节）。

一条贯穿全文的判断标准（来自那篇清单）：

> **提示词只是其中一层，且优先级低于工具设计和上下文管理。**
> 一条指令如果只在特定任务需要，就不该进常驻系统提示——该做成技能或工具描述。

# 第 1 部分：整体框架

## 1.0 一件必须先纠正的认知

"session 能替换 skill"是真的（`capabilities/<名>/` + `--capability` / `active_capability` 已实现），但**换 skill 只覆盖那篇清单的一项**：

| 清单条目 | 靠"换 SKILL.md"能解决吗 |
|---|---|
| 提示词分层 | ✅ 换 skill 就是这件事 |
| 输出约束 | ✅ 大部分（产物契约写进 SKILL.md） |
| RAG / agentic retrieval | ✅ 能靠提示词引导用 grep/read |
| 记忆（工作记忆外化） | ⚠️ 一半：SKILL.md 能**要求**它写，落盘机制在框架 |
| 上下文管理（压缩/落盘/裁剪） | ❌ 框架层 |
| **工具设计** | ❌ 框架层——而那篇清单说这是**最高杠杆** |
| 评测与可观测性 | ❌ 框架层 |
| 工程底座（权限/沙箱/版本/降级） | ❌ 框架层 |

**所以：能力包 = `SKILL.md × 5` + `capability.json` + 它需要的框架契约。** 设计一个能力包，必须同时说清"框架要给它什么"。

## 1.1 总体形态

```
┌─ session（可持久化 / 可恢复 / 可回放）────────────────────┐
│  meta.json      目标、当前能力、台账、schema_version        │
│  journal.jsonl  每次模型请求的完整快照（可重建 / 可回放）    │
│  tasks.jsonl    任务边界（每段的输入、结论、耗时、成本）      │
└──────────────────────────────────────────────────────────┘
        │ 每个任务
        ▼
┌─ ReActLoop（五阶段状态机，硬编码，不扩展）──────────────────┐
│  THINK → PLAN → ACT → OBSERVE → VERIFY                    │
│  每阶段：能力包的 <槽位>/SKILL.md 提供提示词                  │
└──────────────────────────────────────────────────────────┘
        │ 由 capability 决定提示词与约定
        ▼
┌─ 能力包（当前：default / coding）──────────────────────────┐
│  capabilities/<名>/{think,plan,act,observe,verify}/SKILL.md │
│  capabilities/<名>/capability.json   ← conventions          │
└──────────────────────────────────────────────────────────┘
```

**三条不可动的约束**（都来自现有代码，改它们等于改产品）：

| 约束 | 依据 |
|---|---|
| 五阶段固定，不可新增 | `loop.py` 的转换与 gate 分支按阶段名硬编码 |
| 每个任务 `context.reset()`，段间只能靠落盘制品 | [loop.py:475](../../react/loop.py) |
| `system` 逐字节静态（缓存契约） | [context.py:401](../../react/context.py)；实测命中率 90% |

## 1.2 九项关注点在框架层的位置

| # | 关注点 | 现状 | 框架层设计（本次要做的） |
|---|---|---|---|
| 1 | 上下文管理 | 压缩 ✅（token 压力触发）；裁剪 ⚠️（仅 4000 字符截断） | **上下文五层**（见 §1.3）；`spill`（大输出只回路径+摘要）；压缩作为**可检测的锁操作** |
| 2 | 提示词 | 分层 ✅（system 静态 / 能力约定 / skill 正文 / 步骤指令） | **补一层"工程记忆"**（§1.3 第 4 层）；工具描述按"何时用/何时不用"重写 |
| 3 | 记忆 | 会话摘要 ✅（600 字符）；工作记忆 ❌ | **工作记忆外化成落盘实体**（`work.md`）；session 日志（§1.1） |
| 4 | RAG | 无 | **明确不做向量检索**：走 agentic retrieval（grep/read/glob 自己查） |
| 5 | 工具设计 | 6 个工具，描述偏"参数含义" | **补齐工具集**（`patch`、`run_tests`）；`write` 加体积护栏；描述写"何时用/何时不用" |
| 6 | 输出约束 | 部分（`[RESULT]`/`submit_verdict` schema） | **产物契约**：可机械检查的落盘产物（覆盖声明、回执、台账进度） |
| 7 | 评测与可观测性 | token_stats ✅；回放 ❌ | **录制回放**：journal → Mock 重放；分层评测（见 §1.6） |
| 8 | 工程底座 | work_dir 边界 ✅、shell 门禁 ✅、沙箱 ⚠️（作业对象隔离失效） | 格式 `schema_version` 与迁移；按段归因成本；可控降级 |
| 9 | 多 agent | 未做 | **不做**（那篇清单也说"单 agent 跑顺了再谈"） |

## 1.3 上下文：五层预算模型

现在实际是三层（system → 历史 → 尾部注入）。设计成五层，关键是新增第 4 层：

| 层 | 内容 | 变化频率 | 位置 |
|---|---|---|---|
| 1 | system（全局协议 + 运行环境） | **永不变** | messages[0] |
| 2 | 能力约定（`conventions`） | 换能力时变 | 尾部 user，skill 正文之后 |
| 3 | 编号台账（`R1..Rn`，契约） | 台账变更时 | 尾部 user |
| 4 | **工作记忆（工程事实板）** ← 新增 | 每次 ACT 后可能变 | 尾部 user，台账之后 |
| 5 | 最近历史 + 当前步骤指令 | 每步变 | 尾部 user 最后 |

**核心原则：进入上下文的不是代码，而是"路径 + 符号 + 事实"。** 代码按需 `read`，不驻留。

**为什么第 4 层必须在尾部而不是 system**：system 一旦变，前缀缓存全废（那是我们花了几轮才修好的东西）。工作记忆会随 ACT 更新，只能放在"离前缀最远"的位置——与 `_digest_text` 的处理同理。

## 1.4 记忆：三类，各有着落

| 类型 | 载体 | 生命周期 |
|---|---|---|
| 会话内 | `SessionContext.messages` | 一个任务（`reset()` 清空） |
| **工作记忆** | `<work_dir>/.react-agent/work.md` | 跨任务、抗压缩（本次新增） |
| 会话日志 | `data/sessions/<sid>/` | 跨进程（可恢复 / 可回放） |

## 1.5 工具：执行管线

那篇清单要求"前置校验 → 执行 → 后置处理"三段式。现状是 `run_tool` 一个函数直接分发。设计：

```
run_tool(name, args)
  ├─ 前置校验：参数 schema / 边界（越界拒绝）/ 体积护栏（write 超大→提示用 patch）
  ├─ 执行：真实动作
  └─ 后置处理：回执结构化 + 截断（超 4000 字符落盘，只回路径与摘要）
```

## 1.6 评测：三层

| 层 | 内容 | 现状 |
|---|---|---|
| L1 确定性断言 | `--smoke`（100+ 条） | ✅ 已有 |
| L2 录制回放 | journal → Mock 重放（改提示词/工具后比对） | ❌ 待建（依赖 session 日志） |
| L3 黄金用例 | 3~5 个真实任务的输入/产出快照 | ❌ 待建 |

**L3 是最便宜的起点**：记下"输入（任务/台账）+ 产出（文件哈希 + 测试 exit）"，改完重跑对比——不需要完整回放就能挡住回归。

## 1.7 工程底座

| 项 | 设计 |
|---|---|
| 权限 | `work_dir` 是唯一边界（文件工具 + shell 同一约束）；无白名单、无"关边界"开关 |
| 沙箱 | OS 级（受限令牌 + 作业对象）；**已知缺陷：作业对象隔离失效**（`kill-on-close`/内存上限设置失败） |
| 版本 | 所有落盘格式带 `schema_version`，附迁移路径 |
| 成本 | `token_stats` 已有；补**按段归因**（哪一段贵） |
| 降级 | 执行器未启用 / 模型不可用 / 工具超时时，明确"未实测"而不谎称完成 |

## 1.8 框架层实施顺序

| 步 | 内容 | 依赖 |
|---|---|---|
| F1 | **能力选择暴露到界面**（`/api/session` 返回能力清单 + 设置下拉） | 无 |
| F2 | **工具补齐**（`patch`、`run_tests`、`write` 护栏、描述重写） | 无 |
| F3 | **工作记忆落盘** + 注入第 4 层 | F2（产物来自工具） |
| F4 | **session 日志**（meta + journal + tasks，可恢复可回放） | F3（要记的实体先存在） |
| F5 | **录制回放 L2/L3** | F4 |
| F6 | 压缩锁 / spill / prune（按需，当前规模未到瓶颈） | F1–F3 |

# 第 2 部分：编码能力（本次要做的）

> ⚠️ **本节（含 §2.5 C1–C5）已被 [编码能力设计](2026-09-29-coding-capability-design.md) 取代。**
> 原因：本节的出发点是"贴着现有代码找缺口"（`write` 缺护栏 → 加护栏，等等），
> 而正确的出发点应当是**能力要对什么作出保证**。新文档从保证出发重写了契约与优先级，
> 并把"验收判据由上游需求能力提供""先做从零建工程"两个已确认的前提纳入。
> 本节保留作为**演进留痕**：它记录的实测依据（29,056 token 重写等）仍然有效并被新文档引用。

## 2.1 能力包的契约

| | 内容 |
|---|---|
| **输入** | ① 编号台账（有就用）；② 或原始任务描述（**能力自己产出台账**） |
| **产出** | ① `work_dir` 里可运行代码 + 测试；② **覆盖声明**（`R<n> → 文件:符号`）；③ **真实测试回执**；④ **工作记忆**（落盘）；⑤ 缺口与假设 |
| **不负责** | 需求的澄清与确认（那是需求能力）；独立验收结论（那是 QA 能力） |

**边界说明**：编码能力**必须**产出覆盖声明，但**不得**自己宣布"验收通过"——那留给 QA。这是能力的职责切分，也避免"自证"。

## 2.2 九项关注点在编码段的落实

| # | 关注点 | 编码段的设计 |
|---|---|---|
| 1 | 上下文 | 台账 + 工作记忆常驻；**代码只进路径**；大文件读用 `offset/limit`；跨任务靠 `work.md` |
| 2 | 提示词 | `conventions`（技术栈/规范）+ 5 份 SKILL.md；**规范只留可机械判定的条目** |
| 3 | 记忆 | `work.md`：目录结构 / 台账进度 / 已改文件 / 最近验证 / 关键决策 |
| 4 | RAG | 不用；靠 `grep` + `read` 自己定位 |
| 5 | 工具 | `patch`（替代整文件重写）、`run_tests`（结构化验证）、`edit` 增强（多处替换） |
| 6 | 输出约束 | 覆盖声明 / 测试回执 / 台账进度三项可机械检查 |
| 7 | 评测 | L1（已有）+ **L3 便宜版**（编码会话输入产出快照） |
| 8 | 工程底座 | 边界与沙箱由框架提供；`work.md` 带 schema_version |

## 2.3 实测依据（两次真实运行）

| 现象 | 数据 | 结论 |
|---|---|---|
| 整体重写文件 | 单次输出 **29,056 token**、耗时 **106.6s**（逼近 120s 调用超时） | `write` 缺体积护栏 → 需要 `patch` |
| 规范被忽略 | `conventions` 已注入（997 字符），但 8 字段头 **0 处**、无覆盖声明 | **散文规范不可靠** → 要可机械检查的产物 |
| 压缩曾失效 | 单次 prompt 最大 **158,789**（阈值 100k），命中率 58% | 已修（补 token 维度），修复后最大 97,445、命中 90% |
| 完成无证据 | `pytest -q` 只能手工跑，回执是非结构化文本 | 需要 `run_tests` |

## 2.4 已决议：取消 8 字段头

两次真实运行，条件规则（≥10 函数才启用）已注入，**都没执行**（8 字段头 0 处）。**决议：取消。**

理由：它是为"多函数协作、需跨函数字段归属分析"设计的，与当前"单文件 CLI 工具"的规模不匹配；两次实测都证明它在该规模下不会被采用。取消后：

- 从 `capabilities/coding/capability.json` 的 `conventions` 移除 `header_style` / `header_applies_when` 与 `definition_of_done` 里对应那条
- 从 `coding` 五份 SKILL.md 移除 8 字段头章节与 7 规则核对（`plan` 的"是否启用"判定段、`act` 的头部规范、`observe` 的 7 规则、`verify` 的"头一致性"项）
- **保留**"函数职责清晰 + 参数/返回/异常写清"这一类**可机械判定**的要求（普通 docstring）
- 需要该方法论时，作为**独立能力**（如 `coding-structured`）再引入，不占默认编码包

## 2.5 编码段实施顺序

| 步 | 内容 | 验收 |
|---|---|---|
| C1 | **工具补齐**（`patch` / `run_tests` / `write` 护栏 / 描述重写） | 断言：超大 `write` 被拒并提示；`patch` 能改文件且只发变更；`run_tests` 回结构化结果 |
| C2 | **工作记忆落盘**（`work.md` + 注入第 4 层） | 断言：跨任务能读到上一任务写的 `work.md`；system 仍逐字节静态 |
| C3 | **产物契约**（覆盖声明 / 回执 / 台账进度） | 断言：缺覆盖声明时 OBSERVE 判缺陷 |
| C4 | **评测 L3 便宜版**（编码会话输入产出快照） | 断言：改动前后快照可比对 |
| C5 | **真实任务复测** | 用一个空目录跑 CSV 去重任务，对比 C1–C4 前后的 token / 命中率 / 产物质量 |

## 2.6 明确不做

- ❌ 向量检索 / RAG（那篇清单第一条误区）
- ❌ 多 agent / 并行
- ❌ 新增阶段（改状态机）
- ❌ 让编码能力自己宣布"验收通过"（那是 QA 的职责）
- ❌ 段间流水线（用户明确要求一个一个做，不在本次）

# 第 3 部分：后续能力（只定边界）

## 3.1 职责切分

| 能力 | 输入 | 产出 | 明确不做 |
|---|---|---|---|
| **编码**（本次） | 台账 or 任务描述 | 代码 + 覆盖声明 + 回执 | 不澄清需求、不宣布验收 |
| **需求理解**（后续） | 用户原话 | 编号台账（R1..Rn + 验收 + 落点） | 不写代码 |
| **QA 审查**（后续） | 台账 + 代码 | 逐条独立判定 + 证据 | 不修代码（只判定） |

## 3.2 留给后续的接口

编码能力**现在就要**按"可能拿到台账"设计（有则用、无则自产），这样需求能力接入时**编码包不用改**。这是本次设计里唯一为后续预留的点。

## 0. 本文档为什么重写

前一版（架构文档 §2）的落点是**贴着现有代码找缺口**：`write` 缺护栏 → 加护栏；`shell` 回执非结构化 → 加 `run_tests`；`reset()` 会清空 → 加 `work.md`。

那是对的现象，但**起点错了**。起点应当是**这个能力要对什么作出保证**；机制是推导出来的结果。

三个已确认的前提（决定了设计的严格程度）：

| # | 前提 | 推论 |
|---|---|---|
| **1** | 这是要**发布的产品**，不是自用助手 | 不能靠人看一眼兜底 → **必须机械可验** |
| **2** | 验收判据**由上游「需求」能力提供** | 判据是**输入**，能力不得自产、不得猜 |
| **3** | 先做**从零建工程**模式 | 暂不背"不许破坏既有行为"的负担 |

---

## 1. 保证

> **产出的工程，每条需求都有一次真实执行的验收结果作为证据；全绿才算完成；任何未执行或失败都必须在交付物里可见。**

三条拆开：

| | 保证 | 反例（现状会怎样） |
|---|---|---|
| G1 | 每条需求都有**可执行**的验收判据 | 判据是散文"应正确处理边界" → 无法验，却照样声称完成 |
| G2 | 每条判据都**真的被执行过**，回执留存 | 模型自称"已实现并测试通过" |
| G3 | 未覆盖 / 未执行 / 失败 **必须可见** | 交付物只列做成的，漏掉的和没验的都不提 |

**G3 是最容易被漏的一条**，也是产品化的底线：交付物要能让人看出**哪里没做**。

---

## 2. 契约：编码能力要求上游给什么

因为前提 2，能力**消费**一个结构化输入。这是两个能力之间的接口，必须在**本文档定死**（否则上游怎么写都不知道）。

```yaml
# 输入：requirement-set（由「需求」能力产出，落盘为 spec.md 的机器可读段）
schema_version: 1
goal: 一句话目标
unit:                     # 需求单元，可多级
  - id: R1
    statement: 找出 CSV 中内容完全重复的行
    acceptance:           # ★ 必须是可执行的
      kind: command       # command | predicate
      run: python -m pytest tests/test_core.py -q
      expect: exit_code == 0
    artifacts:            # 期望存在的产物（可选）
      - src/csvdup/core.py
  - id: R2
    statement: 默认只统计，不修改文件
    acceptance:
      kind: command
      run: python -m pytest tests/test_core.py::test_no_write_by_default -q
      expect: exit_code == 0
out_of_scope:             # 明确不做的，防止 agent 自行扩张
  - 不做 GUI
```

**对 `acceptance` 的硬要求**（这是 G1 的落地）：

| 要求 | 说明 |
|---|---|
| **必须有 `run` 与 `expect`** | 只有 `statement` 的条目**不算可验收** |
| `kind: command` | 一条可执行的命令 + 期望（`exit_code == N` 或输出含某串） |
| `kind: predicate` | 结构化断言（如 `file_exists(路径)`），由能力内置的检查器执行 |
| **不可验收的条目** | 能力**必须报告为"无法验收"并要求上游补**——**不得**自行脑补判据、**不得**静默跳过 |

**"能力不得自产判据"是刻意的边界**：判据是需求的表达，由上游负责；编码能力猜判据等于替需求做决定，错了还没人知道。

**没有上游时的降级**：允许直接给一段任务描述（人话）。此时能力**先做一次"判据化"**，把描述拆成 `R<n>` + 可执行判据，**并把结果交人确认**；未经确认不得进入实现。这是"自产判据"的唯一合法形式——**它产的是提议，不是事实**。

## 3. 完成判据是系统概念，不是散文

G2 的落地：把"完成"从**模型的判断**变成**系统的事实**。

```
完成 = ∀ R: 该 R 的 acceptance 已执行 ∧ 结果满足 expect
```

| 环节 | 现状 | 设计 |
|---|---|---|
| 执行判据 | `pytest -q` 靠模型手拼命令；回执是非结构化文本（`exit=0\n<输出…>`） | **能力内置验收执行**：按 `R<n>` 逐条跑判据，收集结构化回执 |
| 判定 | 模型读文本，自称通过 | **系统按 `expect` 判定**，形成 per-R 的 `pass/fail/not_run` |
| 收尾 | 模型写总结 | **交付物由证据生成**：逐条 R 列状态与回执 |

**关键：现状里"35 passed"这条信息是存在过的**（真实运行里出现过），但它只是一段文本，**系统不认识它**。所以"完成"取决于谁在读书——这正是要消灭的。

## 4. 交付物（四条，可机械核对）

| # | 交付物 | 生成方式 | 机械核对 |
|---|---|---|---|
| 1 | `work_dir` 里的工程 | agent 产出 | — |
| 2 | **逐条覆盖表** | **由证据生成**，不是手写 | 每个 R 都有状态 |
| 3 | **验收回执**（含命令、exit、输出摘要） | 执行判据时采集 | 每条回执对应一个 `run` |
| 4 | **缺口清单** | 未覆盖 / 无法验收 / `out_of_scope` | **必须显式列出**，空也要写"无" |

覆盖表形态（第 2 项）：

```markdown
| R | 状态 | 证据 |
|---|---|---|
| R1 | ✅ pass | `pytest tests/test_core.py -q` → exit 0 |
| R2 | ❌ fail | `pytest ...::test_no_write_by_default` → exit 1 |
| R3 | ⚠️ not_run | 判据缺失（上游未提供），已报缺口 |
```

**第 2 项"由证据生成"是刻意的**：手写的覆盖声明可以被编造（两次真实运行里，规范注入后被忽略，覆盖声明一处都没有）；**由执行结果生成的表没法编**。

## 5. 机制（现在才是实现手段，全是推导出来的）

| 机制 | 服务于哪条保证 | 依据 |
|---|---|---|
| **验收执行器**（按 R 逐条跑判据、结构化回执） | G2 | §3：现状靠模型手拼命令 + 读文本 |
| **覆盖表生成器**（从回执生成表） | G2/G3 | §4 第 2 项 |
| **判据化**（无上游时把描述拆成 R + 判据，交人确认） | G1 | §2 的降级路径 |
| **缺口检查**（`not_run` 与 `out_of_scope` 必须出现） | G3 | §4 第 4 项 |
| **规范载体** `conventions`（技术栈 / 目录骨架 / 命名 / 验收命令） | 产品化（前提 1） | 换技术栈即换能力，否则只能服务一种栈 |
| 上下文：意图（R 集）+ 证据（回执）常驻，**代码只进路径** | 支撑上面全部 | 预算有限；代码驻留会挤掉证据 |
| 记忆：`work.md` 承载"证据链"（每个 R 的实现位置 + 最近回执） | G2 跨任务 | `reset()` 会清空账本 |
| 工具集：读写/搜索/执行 | 手段 | **注意：`patch` 这类效率工具**优先级在后（§7） |

**`schema_version`**：输入 `requirement-set`、覆盖表、回执三段格式都带版本号（产品化后上游/下游版本会漂移）。

## 6. 验收（本文档自己怎么算做成了）

| 验收项 | 判据（可执行） |
|---|---|
| A1 | 给一份**判据完整**的 `requirement-set`（如 `docs/demo-brief.md` 的 dupfinder），能产出工程 + 覆盖表 + 回执 + 缺口清单 |
| A2 | 覆盖表的每一行都能**追到一次真实执行**（回执里的命令与 exit 与之对应） |
| A3 | **故意让 R2 的判据失败** → 覆盖表必须显示 ❌，且交付物**不得**声称完成 |
| A4 | 给一份**含散文判据**的 `requirement-set`（某条只有 `statement`）→ 必须报"无法验收"，**不得**静默跳过或脑补 |
| A5 | 给**只有任务描述**的输入 → 先产出判据化提议并要求确认；**未确认时不得进入实现** |
| A6 | 由证据生成的覆盖表**不可被模型文字覆盖**（手工改判据执行结果不会改变表） |

**A3 / A4 / A5 是反向验证**：它们检查的是"失败时是否可见"，而不是"顺利时能不能过"。
产品化下**这类负向验收比正向更重要**——正向在演示里总能过，负向才决定产品可信。

## 7. 优先级（相对前一版有改动，理由明确）

| 序 | 做什么 | 为什么在这个位置 | 状态 |
|---|---|---|---|
| **1** | **验收执行器 + 覆盖表生成器 + 缺口检查** | 直接对应 G2/G3；没有它，"完成"仍取决于谁在读书 | ✅ 已实施（`react/acceptance.py` + `--verify`） |
| **2** | **输入契约（`requirement-set`）与判据化** | G1；也是与上游能力的接口 | ✅ 已实施（规范位置 + 确认门禁 + `--intake` / `--confirm-spec`） |
| **3** | **规范载体 `conventions` 重整**（含取消 8 字段头） | 产品化的多技术栈前提 | ✅ 已实施（能力升 v2.0.0；新增 `docstring`/`acceptance` 契约字段；8 字段头与 7 规则全部移除） |
| **4** | **记忆承载证据链**（`work.md`） | 让证据跨任务活下来 | ⬜ 未开工 |
| **5** | 上下文分层收尾 | 支撑上面 | ⬜ 未开工 |
| **6** | **效率工具（`patch` 等）** | **只管速度与成本，不解决正确性**——故在后 | ⬜ 未开工 |

**实施说明（与原文的差异，实施中发现后调整的）**：

- 格式从 YAML 改为 **JSON**：本项目 `pyyaml` 不可用（已核实），`json` 是标准库，
  `json.loads` 本身就是一层 schema 校验。
- 第 1 项实施中修掉两个真问题：`all_passed` 原本依赖"证据数量等于单元数量"（脆弱，
  漏执行一条同时少一条回执就会被算通过）；"命令不存在"被误判为 `fail`（应为 `error`）。
- 第 2 项新增用户可见的 `--intake` **要求描述写成文件**（避免 shell 引号问题），
  以及 `--confirm-spec` 作为**独立**确认动作——刻意不做隐式确认。
- 第 3 项实施中发现一个真漏洞：`CONVENTION_FIELDS` 是**硬白名单**，不在表里的键会被
  `clean_conventions` **静默丢弃**。新加的 `docstring` / `acceptance` 一开始就是这样
  被丢掉的——"写了却不生效"比没写更糟（声明的规范不生效，等于整套规范失信）。
  已修白名单，并加断言"capability.json 里的每个 convention 键都必须在白名单里"。
  这条断言对所有能力生效，不只 coding。

## 8. 明确不做

| 不做 | 原因 |
|---|---|
| **改已有工程模式** | 本次先做从零建（前提 3）。它需要"改动前基线""不许破坏既有行为"等额外概念 |
| 能力**自产**验收判据 | 判据是上游职责（前提 2）；只允许"产提议交人确认" |
| 让模型**文字**宣布完成 | G2：完成由执行证据定义 |
| 向量检索 / RAG | 判据与代码都是 agentic retrieval 足够（grep/read） |
| 多 agent | 单能力先做对 |
| 8 字段函数头 | 已决议取消（两次实测均未执行） |

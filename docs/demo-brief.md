# 示例任务书：dupfinder（文件去重 CLI）

> 用途：给 react-agent 的一份完整任务输入，用来试它的
> PLAN 拆解 / `[方案]` 自证 / ACT 写码 / OBSERVE 核对 全链路。
> 下面「任务书」一节可整段直接粘贴到 Web 对话框。

---

## 一、任务书（直接粘贴这段）

```
目标：实现一个命令行工具 dupfinder，扫描指定目录，找出内容完全重复的文件并分组报告；
     默认只报告不动手，加 --delete 才真正删除。

约束：
  - Python 3.11+，仅用标准库（hashlib / os / argparse / json），零第三方依赖
  - 一个核心模块 + 一个 CLI 入口，总代码量控制在 300 行以内
  - 10000 个文件、总计约 2GB 的样本下，扫描耗时应 < 30 秒
  - 必须能在 Windows 上跑：处理路径分隔符、无读权限、扫描中文件被删这三类情况

验收（必须可验证）：
  1. `python -m dupfinder <dir>` 输出重复分组，且每组内文件内容字节级完全相同
  2. 支持 `--json` 输出机器可读格式
  3. 只有显式加 `--delete` 才删文件；默认每组保留第一个、删除其余；
     删除前必须先把将要删除的清单打印出来
  4. 自带测试：构造 20 个文件（含 3 组重复、含 2 个空文件、含同名不同内容、
     含子目录），用标准库 unittest，`python -m unittest` 全部通过
  5. 遇到无读权限或扫描中消失的文件不得崩溃，计入 warnings 并在最后汇总

已知：
  - 工作目录为空，从零开始
  - 不要求处理符号链接造成的目录循环，遇到就跳过并给出警告

不要：
  - 不做 GUI / Web 界面
  - 不做增量索引或数据库缓存，一次性扫描即可
  - 不联网
  - 不要默认引入并发——单线程即可；如果你认为必须并发，请在方案里论证并对比
```

## 二、为什么这份任务书能试出它的能力

| 任务书里的要求 | 会触发什么 |
|---|---|
| 目标 + 不要 | THINK 判断需要多步 → 走 PLAN 拆解 |
| 300 行 / 30 秒 / 标准库 | PLAN 每步的**完成标准**，OBSERVE 拿它当尺子 |
| 哈希算法选哪个 | `[方案]` 自证：md5 / sha256 / blake2b 的速度与碰撞权衡对比 |
| 2GB / 10000 文件要 <30 秒 | `[方案]` 自证：先按文件大小分组再哈希（跳过唯一大小） vs 全量哈希 |
| 是否并发 | `[方案]` 自证：被明确要求论证，不能拍脑袋 |
| `--delete` 的安全性 | `[方案]` 自证：硬删 / 移回收站 / 只报告 的对比，适用边界 |
| `unittest` 全绿 | ACT 写完后可用 `[EXEC: shell]` 真跑测试，OBSERVE 看**真实回显**而非模型的自我感觉 |

第 7 条最关键：**它有真实执行通道，所以"测试通过"是跑出来的，不是它自己说的。**

## 四、怎么判断它跑得好不好

看这几处，能直接反映出框架的成色：

1. **PLAN 之后会停一次**（`plan` 档的默认行为）——这时看步骤拆得合不合理、每步有没有可判定的完成标准
2. **ACT 里有没有 `[方案]` 卡片**——至少应在「哈希算法」「先按大小分组」「删除策略」三处出现，且每张都要有备选对比
3. **OBSERVE 有没有判过 defect**——判过反而说明质检在工作；一次都不判要警惕它在一味说好
4. **有没有真的跑测试**——状态区应出现执行回显，而不是只有文字
5. **全程被打断几次**——正常应是个位数；如果十几二十次，说明闸门档位或计划被返工了

## 五、想再难一点，可以追加这些

任选一条追加到任务书末尾，难度和表现力都会上一个台阶：

- 支持 `--min-size` / `--exclude <glob>` 过滤
- 重复组按「总可释放空间」排序输出
- 输出 HTML 报告（引入 `html` 转义与模板，又是一处方案选择）
- 支持把上次结果存成 JSON，下次只重扫新增文件（这时「要不要做增量索引」就成了真正的方案权衡）
